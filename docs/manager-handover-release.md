# Передача дел менеджера: локальная готовность

Дата: 04.10.2026. Механизм подготовлен в коде; фактическая передача Ахботы не выполнялась.

## Работа директора

Раздел `/employee-handovers` открывается основателю. Директор создаёт отдельный **неактивный** аккаунт нового менеджера через «Сотрудники», выбирает прежнего и нового менеджеров, дату, категории и читает предварительный список. До ручного подтверждения после этой даты данные и доступ не меняются. Подготовленный план можно изменить или отменить.

При подтверждении все выбранные текущие записи и учётные записи меняются в одной транзакции. Несовпадение списка с предварительным просмотром отменяет операцию. Открытые кассовые смены, задачи маркетинга и кандидаты подбора блокируют подтверждение до ручного решения, поскольку обычный менеджер не имеет к ним нужного доступа. Документы сохраняют автора, планы продаж сохраняют исторические цели; эти исключения показываются директору. У нового менеджера появляется уведомление.

Продажа и заявка относятся к менеджеру на дату регистрации. Действия после перехода относятся к тому, кто отвечал за запись в день действия. Архивный профиль прежнего менеджера остаётся в KPI и отчётах за период его работы. В карточках клиента, заказа и задачи сохраняется запись о передаче.

Автоматический откат доступен только пока новый менеджер не входил и переданные записи не изменились. При несовместимых изменениях API отвечает конфликтом; директор разбирает записи вручную.

## Что проверено локально

- `prisma validate` и `prisma generate` — успешно.
- SQL миграции сопоставлен с `prisma migrate diff` от прежней схемы.
- `tsc --noEmit`, ESLint изменённых файлов, тест шести сценариев временной атрибуции, статический тест изоляции компаний и `next build` — успешно.
- Три независимых сквозных прогона `npm run test:employee-handover:e2e` на отдельной локальной PostgreSQL базе прошли. Создавались только помеченные тестовые сотрудники и записи: подготовка и отмена плана, запрет подтверждения до срока, отказ при изменении списка, атомарная передача шести категорий, переключение доступа, KPI и отчёты по старому и новому владельцу, журнал, безопасный откат и запрет отката после новой работы.
- Тест входил через локальный Next.js сервер под директором и обоими менеджерами, проверял страницы и API передачи, KPI, отчётов, заявок и заказов. После каждого прогона тестовые записи удалялись; настоящая Ахбота не менялась.
- В сквозном прогоне найден и исправлен ответ 500 у API передачи: теперь маршруты явно устанавливают контекст компании. Доступ к странице передачи ограничен основателем на уровне маршрута.
- Миграции на пустой локальной базе не дошли до новой миграции: прежняя `20261001190000_assign_director_operating_regulation` требует заранее существующих реальной компании, основателя и операционного директора. Это ограничение тестовой среды, а не подтверждение результата новой миграции.
- Команда `prisma db push --accept-data-loss` была отклонена автоматической проверкой как потенциально разрушающая; повторять её без отдельного разрешения нельзя.

## Перед публикацией

1. Дождаться снятия лимита Vercel; выполнить одну проверку доступности публикации. Не создавать повторные deployments и не подменять production Preview-версией.
2. На разрешённой базе проверить прохождение **цепочки миграций** с её реальными исходными данными. Локальный сквозной тест использовал схему, созданную из текущего `schema.prisma`; он не доказывает, что вся историческая цепочка миграций применится к рабочей базе.
3. После отдельного разрешения пользователя выполнить один согласованный выпуск и проверить `https://orda-erp-staging.vercel.app` и `/api/health`.
4. Фактическую замену Ахботы выполнять только после создания настоящего нового аккаунта и отдельного подтверждения директора.
