# Реагирование на инциденты

## Роли

Владелец бизнеса принимает решения о простое, уведомлениях и данных. Technical Admin локализует, сохраняет доказательства, выполняет rollback/restore. Project Manager подтверждает бизнес-влияние без доступа к секретам.

## Порядок

1. Зафиксировать UTC-время, deployment SHA, затронутые роли/endpoints и request ids; не копировать секреты.
2. Ограничить ущерб: отключить скомпрометированную учётную запись, остановить deploy, отозвать конкретный токен или временно закрыть функцию.
3. Проверить Vercel Runtime Logs, deployment events, Neon metrics/logs и `AuthAuditEvent`.
4. Определить: утечка доступа, потеря/искажение данных, недоступность или supply-chain.
5. Восстановить последнюю известную безопасную версию; для данных использовать процедуру BACKUP_RESTORE только на новой ветке до одобрения production cutover.
6. Проверить health, критические кабинеты, ownership и финансовые инварианты.
7. Составить postmortem: причина, временная шкала, объём, исправление, предотвращение.

## Утечка секрета

Сначала отозвать/заменить конкретный секрет у провайдера, затем обновить нужные Vercel scopes и redeploy. Для `NEXTAUTH_SECRET` учитывать принудительный выход всех пользователей. Проверить Git history и логи; удаление строки из последнего коммита не заменяет rotation.

## Приоритеты

P0: подтверждённая утечка/несанкционированные финансовые операции — немедленная изоляция. P1: production недоступен или повреждение данных — восстановление в пределах согласованных RTO/RPO. P2: ограниченная функциональная деградация — безопасный workaround и плановый fix.
