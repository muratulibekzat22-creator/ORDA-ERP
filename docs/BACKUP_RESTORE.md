# Backup и восстановление

## Цели

До утверждения владельцем рабочие ориентиры: RPO 24 часа и RTO 4 часа. Для ежедневной ERP-работы рекомендуется утвердить RPO не более 1 часа и RTO не более 2 часов; это может потребовать платного restore window.

## Backup

1. Владелец Neon подтверждает тариф, защищённость production branch и реальный restore window.
2. Перед миграцией создать timestamped branch из production в доступном окне восстановления.
3. Ежедневно выполнять логический `pg_dump` из read-only/минимально привилегированного подключения в зашифрованное хранилище, не в Git и не на общий ПК.
4. Хранить минимум 7 ежедневных и 4 недельных копии после утверждения политики.
5. Blob инвентаризировать отдельно: БД содержит metadata, но не заменяет резервную копию содержимого файлов.
6. Записать время, размер, checksum и статус без connection string.

## Restore drill

1. Никогда не восстанавливать поверх production во время проверки.
2. Создать изолированную тестовую branch/database.
3. Восстановить dump или создать branch на выбранный момент.
4. Применить ожидаемые migrations, выполнить Prisma validate/status.
5. Запустить security/business smoke tests с тестовым URL.
6. Сверить количества ключевых таблиц, несколько заказов, платежные суммы и ссылки Blob без раскрытия данных.
7. Удаление тестовой ветки выполняется владельцем после подтверждения результата.

## Аварийное переключение

Остановить записи, определить последний корректный момент, создать восстановленную ветку, проверить её, затем только по решению владельца заменить production connection string и redeploy. Исходную ветку сохранить для расследования. Возврат выполняется тем же способом, без `migrate reset`.

Backup не считается готовым, пока первый restore drill не завершён и не зафиксированы фактические RPO/RTO.
